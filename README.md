# Didgeridoo

Система управления задачами для персональной и командной работы.

Didgeridoo позволяет организовывать задачи в независимых пространствах, распределять их между участниками, отслеживать выполнение и анализировать результаты работы.

**Статус проекта:** в разработке.

## Технологии

- Java 25
- Spring Boot
- Spring Web MVC
- Spring Data JPA / Hibernate
- Jakarta Bean Validation
- PostgreSQL
- Flyway
- OpenAPI 3.1
- Maven
- Docker Compose
- Testcontainers

## Локальный запуск

### Подготовка

Нужен Docker с поддержкой Docker Compose. Для запуска бэка вне контейнера также нужен JDK 25.

Из корня репозитория один раз создать `.env` из `.env.example` и задать локальный пароль БД. Если `.env` уже существует, сохранить его параметры:

```bash
cp .env.example .env
```

`.env` не коммитится и не попадает в Docker-образ. Параметры существующей базы не меняются автоматически при редактировании `.env`.

### Вариант A: бэк и PostgreSQL в Docker

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f backend
```

Compose собирает бэк на Java 17 и запускает его после готовности PostgreSQL. HTTP доступен на `http://localhost:8080`; порт можно изменить через `APP_PORT` в `.env`. Внутри Docker бэк подключается к `postgres:5432`, независимо от внешнего `DB_PORT`.

В текущем приложении нет страницы `/`, поэтому ответ `404` на неё ожидаем. Успешный старт подтверждается строкой `Started DidgeridooApplication` в логах.

После изменения Java-кода образ нужно пересобрать:

```bash
docker compose up --build -d backend
```

Dockerfile сначала собирает JAR через Maven Wrapper на JDK 17, затем копирует его в образ с JRE 17. При сборке образа проверяется форматирование, а тесты с Testcontainers выполняются отдельно на хосте. Docker-сборка не заменяет полный `bash ./mvnw clean verify` перед PR.

### Вариант B: PostgreSQL в Docker, бэк в IDEA/Maven

Если контейнер бэка уже запущен, сначала остановить его, чтобы освободить 8080:

```bash
docker compose stop backend
docker compose up -d postgres
```

В IDEA выбрать JDK 17 для Project SDK и запуска, а рабочей папкой — корень этого репозитория. Запускать `DidgeridooApplication` через Run/Debug. Для Maven в терминале:

**Windows (PowerShell):**

```powershell
.\mvnw.cmd spring-boot:run
```

**Linux / macOS:**

```bash
bash ./mvnw spring-boot:run
```

### Остановка

```bash
docker compose down
```

Данные PostgreSQL сохраняются в volume. Флаг `-v` удаляет данные и для обычной остановки не нужен.

**Linux / macOS:**

Тестовый контейнер создаётся автоматически и удаляется после завершения тестов.

### Хранение задач

Миграция V3 создаёт только таблицы модуля tasks: `task_statuses`, `tasks` и `task_changes`. JPA-сущности и репозитории задач/статусов находятся в `tasks.internal`. Flyway обновляет схему, Hibernate проверяет её через `ddl-auto: validate`.

Модуль spaces пока не предоставлен. Поэтому `space_id` хранится как UUID без внешнего ключа к пространствам; таблицы `spaces` и `space_memberships` эта реализация не создаёт. Составной ключ задачи и статуса уже запрещает использовать статус с другим `space_id`. Внешние ключи к существующим пользователям и согласованность исполнителя с источником назначения также проверяются БД.

При интеграции с модулем spaces отдельная миграция должна добавить внешние ключи к пространствам/участникам после проверки существующих данных. До этого БД не подтверждает существование пространства, членство или роль исполнителя. Это ещё не готовый авторизованный HTTP API; соответствующие проверки будут выполняться сервисами через публичный контракт spaces.

### Инициализация статусов пространства

`tasks.api.StatusInitializer.initialize(spaceId)` создаёт INITIAL и FINAL в одной транзакции и присоединяется к транзакции вызывающего workflow. Это внутренний API модулей: вызывающий код отвечает за создание пространства и доступ. Повторный вызов для пространства с любыми статусами отклоняется; уникальные индексы остаются защитой от конкурентных дублей. Начальные имена `To do` / `Done` выбраны для текущей реализации и могут быть переименованы.

Операция не создаёт пространство или участников и не публикует HTTP endpoint. Полный create-space workflow подключается после появления публичного API spaces.

### Создание задачи (внутренний сервис)

`TaskCreationService` проверяет роли через принадлежащий tasks интерфейс `TaskSpaceAccess`: MEMBER создаёт себе или без исполнителя, OWNER — допустимому MEMBER/OWNER, GUEST и посторонним отказ. Роль читается при каждом вызове. Реальный адаптер к публичному spaces API пока отсутствует: без него создание отклоняется до записи. HTTP endpoint и произвольный actor из запроса не добавлены.

Статус проверяется в рамках пространства; defaults — INITIAL, MEDIUM и выключенный assigneeCanEdit. Создание задачи и CREATED выполняются одной транзакцией; ошибка истории откатывает задачу. История хранит начальные поля как `{field: {old: null, new: value}}`, UUID/даты — строки. Это локальное предложение формата для согласования, не утверждённый командой HTTP-контракт. Теги относятся к следующему срезу и в команду пока не входят. Реальное членство и атомарность относительно параллельного изменения роли требуют интеграции с spaces.

### Чтение задач (внутренний сервис)

`TaskReadingService.get(spaceId, actorId, taskId)` возвращает неизменяемый `TaskView`; поиск ограничен пространством. `list(spaceId, actorId, page, size)` читает страницу с порядком `createdAt ASC, id ASC`, page от 0, size от 1 до 100 (локальный технический предел). Фильтры и HTTP-контракт пока не добавлены.

Действующие OWNER/MEMBER/GUEST могут читать; посторонним отказ даже для пустого списка. Членство проверяется при каждом вызове. При отсутствующем адаптере spaces чтение отклоняется. Проверки текущего этапа используют тестового поставщика ролей и реальный PostgreSQL; интеграция с spaces и security остаётся отдельным этапом. Отсутствующая задача и задача другого пространства дают одинаковый `NoSuchElementException` после проверки доступа. Эти исключения пока не являются согласованным HTTP-форматом ошибок.

### Редактирование задачи (внутренний сервис)

`TaskEditingService.edit(spaceId, actorId, taskId, EditTask)` заменяет содержание задачи: title и priority обязательны, null в description или deadline очищает поле, null в assigneeCanEdit сохраняет текущее значение флага. Семантика PATCH здесь не определена. Статус, назначение, пространство и создатель этой операцией не меняются; теги пока не реализованы.

OWNER и создатель с действующей ролью MEMBER могут менять содержание и флаг разрешения. Исполнитель с действующей ролью MEMBER и включённым assigneeCanEdit может менять только содержание. GUEST и посторонним отказ; без адаптера spaces операция также отклоняется.

Строка задачи блокируется внутри транзакции. UPDATED содержит только изменённые поля со значениями old/new. Сохранение без изменений не создаёт историю и не меняет updatedAt. Ошибка записи истории откатывает изменение задачи. Блокировка упорядочивает параллельные операции редактирования; обнаружение устаревших HTTP-запросов и согласование с изменением членства требуют дальнейшей интеграции.

### Смена статуса (внутренний сервис)

`TaskStatusChangeService.change(spaceId, actorId, taskId, statusId)` разрешает смену статуса создателю или исполнителю с действующей ролью MEMBER, любому MEMBER для свободной задачи и OWNER. GUEST и посторонним отказ. Это право не зависит от assigneeCanEdit. Задача и выбранный статус должны принадлежать указанному пространству; назначение и содержание не меняются.

Строка задачи блокируется, а смена статуса сохраняется одной транзакцией с UPDATED, содержащим только старое и новое значения statusId. Ошибка истории откатывает статус. Выбор текущего статуса не создаёт историю и не меняет updatedAt. Возврат из FINAL разрешён. Без адаптера spaces операция отклоняется; HTTP, авторизация и интеграция с реальным членством пока не подключены.

### Удаление задачи (внутренний сервис)

`TaskDeletionService.delete(spaceId, actorId, taskId, confirmed)` требует явного подтверждения. Удалить задачу может OWNER или создатель с действующей ролью MEMBER. Право исполнителя на редактирование не даёт права удаления. Задача ищется в рамках пространства и блокируется для записи. Удаление задачи и каскадное удаление её истории входят в одну транзакцию; статусы сохраняются. Корзина и отдельный архив истории удалённых задач не реализованы.

### Чтение истории задачи (внутренний сервис)

`TaskHistoryService.list(spaceId, actorId, taskId, page, size)` доступен действующим OWNER/MEMBER/GUEST. Перед чтением проверяются членство и принадлежность задачи пространству. Страницы начинаются с 0, размер — от 1 до 100; порядок — createdAt ASC, id ASC. Результат содержит неизменяемые снимки событий, включая actorId, время и поля old/new с допустимыми null. После удаления аккаунта actorId может быть null.

Обе операции отклоняются без адаптера spaces. Подтверждение удаления в интерфейсе, получение actorId из авторизации и HTTP-контракт будут подключены отдельно. Текущие проверки используют тестового поставщика ролей и настоящий PostgreSQL.

### Частичное редактирование (подготовка HTTP PATCH)

`TaskEditingService.patch(spaceId, actorId, taskId, TaskPatch)` меняет только переданные поля. TaskPatch — внутренняя команда, не формат JSON: null вместо Field означает отсутствие поля, Field.of(null) — явное очищение description/deadline. Явный null в title, priority или assigneeCanEdit и пустая команда отклоняются.

Слияние с текущими значениями выполняется после блокировки строки внутри той же транзакции, что проверка прав, изменение и UPDATED. Полное редактирование и PATCH используют общие правила прав и истории. Пропущенные поля не затираются; no-op не пишет историю и не меняет updatedAt. Параллельные PATCH разных полей сохраняют оба изменения; это не заменяет проверку версии устаревшей формы клиента. Разбор JSON, неизвестные/повторяющиеся поля, HTTP-ошибки и настоящая авторизация ещё не подключены.

### Ошибки модуля tasks

Внутри tasks используются отдельные типы ошибок: TaskValidationException (неверные данные, при возможности с именем поля), TaskAccessException (NOT_MEMBER или FORBIDDEN), TaskNotFoundException (задача отсутствует в указанном пространстве), TaskDependencyException (SPACES_UNAVAILABLE или INITIAL_STATUS_MISSING), TaskConflictException (повторная инициализация статусов).

Эти типы не содержат HTTP-статусов и не заменяют общую обработку ApiError. Будущий HTTP-адаптер должен различать отсутствие членства и запрещённое действие без разбора текста сообщения. Причины и сообщения остаются внутренними; SQL и непредвиденные ошибки хранения не маскируются под валидацию. Существование пространства и актуальные роли по-прежнему предоставляет адаптер spaces.

### HTTP-чтение задач

Добавлены GET `/api/v1/spaces/{spaceId}/tasks`, GET `/api/v1/spaces/{spaceId}/tasks/{taskId}` и GET `/api/v1/spaces/{spaceId}/tasks/{taskId}/changes`. Ответы списков имеют поля items/page/size/totalElements. Неизвестные, повторяющиеся или пустые query-параметры отклоняются; доступны только page и size у списков.

TaskActorResolver — точка подключения доверенной аутентификации, а не реализация входа. UUID пользователя не извлекается из имени principal, query, заголовка или тела запроса. Без principal возвращается 401; без адаптера аутентификации или spaces — 503. При отсутствии членства и при недоступной задаче возвращается одинаковый 404. Настоящие сессии, principal и членство пока не подключены.

TaskHttpExceptionHandler ограничен контроллерами tasks и возвращает code/message в форме ApiError. Он не меняет общую инфраструктуру обработки ошибок; при её подключении этот локальный обработчик нужно согласовать с ней. Внутренние сообщения исключений не выдаются клиенту. HTTP-тесты проверяют контроллеры, включая путь к настоящему PostgreSQL с тестовыми поставщиками principal/ролей. Общая Spring Security, сессии и CSRF этими тестами не проверяются. Изменяющие HTTP-операции отключены по умолчанию: они требуют подключения общей CSRF-защиты.

### Подготовка изменяющих JSON-запросов

TaskRequestParser разбирает тела создания, частичного редактирования и смены статуса в существующие команды tasks. Разбор строгий: неизвестные и повторяющиеся поля, лишние JSON-значения после тела и преобразование чисел/строк в другие типы запрещены. UUID требуется в полной форме, дедлайн — ISO timestamp с часовым поясом. Обычные ошибки значений содержат имя поля; повреждённый JSON имеет отдельный тип TaskMalformedJsonException.

Пропущенное поле PATCH сохраняется, явный null очищает только description/deadline. Начальный статус и приоритет по умолчанию продолжает выбирать сервис создания. Проверки названия и другие локальные инварианты остаются в модели. Разборщик использует локальный JsonMapper и не меняет общие настройки приложения. Это подготовка границы HTTP: изменяющие endpoints и их CSRF-защита пока не подключены; глобальная инфраструктура не изменялась.

### Изменяющие HTTP-операции (отключены по умолчанию)

Подготовлены POST `/api/v1/spaces/{spaceId}/tasks` (201, Task и Location), PATCH `/api/v1/spaces/{spaceId}/tasks/{taskId}`, PUT `/api/v1/spaces/{spaceId}/tasks/{taskId}/status` (200, Task), DELETE `/api/v1/spaces/{spaceId}/tasks/{taskId}?confirmed=true` (204 без тела).

TaskWritingController регистрируется только при didgeridoo.tasks.http.writes-enabled=true. Включение допустимо после подключения настоящего TaskWriteSecurity и spaces-адаптера. TaskWriteSecurity обязан проверять доверенную сессию и CSRF через общую инфраструктуру и только после успешной проверки возвращать UUID пользователя. Это интерфейс интеграции, не реализация Spring Security. Без principal/действующего пользователя — 401, без адаптера — 503, при отказе CSRF — 403 INVALID_CSRF_TOKEN; бизнес-сервисы при этих отказах не вызываются. Одного свойства включения недостаточно для выполнения операций.

Тела запросов разбираются TaskRequestParser; неизвестные query-параметры запрещены, у DELETE допускается только единственное confirmed=true. Создание возвращает снимок внутри транзакции создания, без отдельного чтения и повторной проверки прав после commit. Изменения задачи и история остаются атомарными в сервисах.

HTTP-тесты используют настоящие сервисы и PostgreSQL, но тестовые адаптеры безопасности и членства и standalone MockMvc. Они подтверждают работу контроллеров и отказ до сервисов, но не проверяют настоящие сессии, CSRF-фильтры или общий servlet/security filter chain. Контроллеры и локальный обработчик ошибок остаются внутри tasks; инфраструктурные модули не изменены. Подключение реальной защиты и общий create-space workflow остаются интеграционным этапом.
